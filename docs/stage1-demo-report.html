1. Setup (chunk 1)

What was built. A plain-JDK project with no dependencies, as the offline rule requires. build, run and test scripts exist for Windows (.bat) and Unix (.sh). They compile from Main with -sourcepath, which handles the spaces in your folder path. The compiler flag --release 17 lets teammates on JDK 17 build the code even though it was written on JDK 21. A .gitignore keeps compiled output and IDE files out of the repository.

Test harness. TestRunner has two check methods and a summary, and exits non-zero on failure. It was chosen over JUnit so that a marker needs only a JDK.

Status. Done. The .sh scripts have not been run on a Mac or Linux machine.

2. Domain layer (chunks 2 and 3)

What was built. 29 files holding all game rules and state. The package never prints, reads input or imports from the other layers, which is what the brief means by keeping rules out of the UI.

GroupClassesKey points
ValuesMoney, MenuItem, Menu, ActionResult, PaymentMoney is integer cents. ActionResult carries success plus an explanation, which is how invalid input gets explained.
CustomersCustomer (abstract), RegularCustomer, CustomerStatusSatisfaction loss, type label and dish choice are overridable. The state methods are package-private and throw if called in the wrong state. Dish rule F1: customer n orders item (n-1) mod 3.
Orders and tablesOrder, OrderStatus, TableThe price is locked when the order is taken. Pasta needs two cooking units; the order becomes READY on the last one.
RestaurantRestaurantOwns tables, queue, customers and scoreboard. Does arrivals, seating, finishing eating, satisfaction loss and walk-outs. Seating logic lives here so a later Host can share it.
StaffStaff, Waiter, Chef, CashierEach validates and executes its tasks and describes what it could do now. The Cashier picks the oldest eligible payer, one per turn.
CommandsWaiterTask, ChefTask, SeatTask, TakeOrderTask, ServeTask, CookTask, WaitTaskOne object per command, so the controller has no command-specific code.
Setting and resultGameConfig, ArrivalSchedule, VictoryTargets, Scoreboard, PriceCalculator, GameOutcomeThe base setting is data. Victory uses integer maths: an average of exactly 60 wins, 59.75 does not.
Rules worth knowing: a customer served on turn t is ready to pay on t+1 and can pay on t+2 at the earliest. A dish finished this turn cannot be served this turn. A customer who reaches satisfaction 0 leaves, the order is cancelled and the table freed. Customers who are eating or paying lose nothing.

Status. Done and tested. No Stage 2 or 3 code is present (a word-match search for VIP, critic, host, combo and happy finds nothing).

3. Control layer (chunk 4)

What was built. GameController (about 80 lines) runs the six-step turn loop for all 18 turns. It sequences calls and contains no rules. For the Waiter and then the Chef, it asks for a task, runs it, shows the result, and repeats until it succeeds. That loop is the whole "invalid input does not use up the turn" feature. ManagerInput is the interface the controller depends on, so the same controller is driven by the keyboard, by a script, or by a test. TurnReport carries the automatic-phase results to the display, including the satisfaction values from before the loss was applied.

Status. Done and tested through full games.

4. Console UI (chunk 4)

ClassJob
CommandParserText to task. Case-insensitive; C and T prefixes are optional; errors name the problem and suggest a fix (for example "'seat' needs a customer id, e.g. 'seat 3' or 'seat 3 1'").
ConsoleViewAll formatting: welcome, board, results, end of turn, final PASS/FAIL checklist. ASCII only, because some Windows consoles garble other characters.
ConsoleInputPrompts, help, status, menu, quit with confirmation. If input ends, remaining prompts wait so the game still finishes.
ScriptedInputReplays a script, echoing each command, skipping blanks and # comments, then falls back to the keyboard.
MainWires everything. Takes an optional script path; exits with code 2 and a message for a missing file or extra arguments.

Status. Done. Display fields follow the plan (D1 and D2). I have not seen the original assignment brief, so I could not check them against its exact wording.

6. Findings

  • No rule bugs found. The plan's hand trace and the code agree on every number, and the random audit never broke an invariant.
  • One real bug found by hand testing, now fixed: a byte-order mark at the start of input made the first command read as unknown. Windows Notepad adds one when saving UTF-8, and PowerShell pipes add one too, so a script saved from Notepad would have shifted every line. Typed and scripted input now ignore it, with tests.
  • A plan check was too loose: the Definition of Done search for "happy" matches the word "unhappy" in the required "Unhappy departures" display. Use a word-match search instead.
  • Documents drifted slightly from the code (new parse error, turn report, victory-target helpers). The class diagram in the plan was updated.
  • Known behaviours, documented: a typo in a script shifts later lines by one; the turn-16 customer cannot pay in time.
